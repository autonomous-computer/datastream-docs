title: "Pay as you go"
description: "Enable metered internal SEC API usage after a bounded evaluation, then monitor the account and wallet that fund requests"

Pay As You Go is the paid path for uneven or early internal usage. Use it after you have tested a representative request and want metered access without a fixed monthly fee.

## Confirm the account before enabling PAYG

Use the API key tied to the organization to read its current billing state and limits. The rate catalog is public and describes current rates rather than that account's billing state:

```bash
curl --fail-with-body -sS -H "x-api-key: $SECAPI_API_KEY" \
  "https://api.secapi.ai/v1/billing"

curl --fail-with-body -sS -H "x-api-key: $SECAPI_API_KEY" \
  "https://api.secapi.ai/v1/limits"

curl --fail-with-body -sS \
  "https://api.secapi.ai/v1/billing/rates"
```

The free allowance provides `100` included calls each month and renews automatically. The response, not a copied example, shows the account's current billing state and available context.

## Enable the paid path

In the signed-in dashboard, choose Pay As You Go, save a card, make the initial credit top-up, and optionally configure auto top-up. The API endpoint for this account settings action is `POST /v1/billing/payg/enable`; it requires the authorized signed-in session rather than an API key.

Once payment is confirmed, the organization moves to `payg_active`. Until then, a billable request can return `402 billing_required` with the account condition that needs attention.

## See the grant boundary before you hit it

The included allowance renews automatically each month. An account without a payment method still stops when the current month's allowance is spent, so from `80%` onward billable responses carry an advisory that lets an integration fund production usage or wait for the next renewal deliberately:

| Header | Meaning |
| --- | --- |
| `SECAPI-Grant-Status` | `approaching` while the grant is nearly spent, `exhausted` once it is gone. |
| `SECAPI-Grant-Consumed-Percent` | Share of the grant consumed, as an integer percent. |
| `SECAPI-Grant-Remaining` | Included calls still available. |
| `SECAPI-Grant-Warning` | Human-readable warning, sent while the status is `approaching`. |
| `SECAPI-Grant-Action` | `add_payment_method_soon`, then `add_payment_method`. |
| `SECAPI-Grant-Action-Url` | Where to add a card or buy credits. |

The advisory accounts for the units the current request itself consumes, so a multi-entity batch call that crosses the threshold reports it on that response rather than on a later one.

These headers are absent once a card is on file or the prepaid wallet holds a positive balance, because the grant is no longer a boundary for that account.

When the grant is spent, the `402 billing_required` response identifies the cause in `details.reason` as `starter_grant_exhausted` and carries `details.grant`, `details.addPaymentMethodUrl`, `details.topUpUrl`, and `details.nextSteps`. Branch on `details.reason` rather than matching the message text. Other `402 billing_required` conditions — a plan entitlement, a budget stop, or a failed payment — use their own reasons and their own resolution paths.

## Meter and monitor real usage

PAYG uses prepaid credits. Read [billing rates](/api-reference/platform/get-v1-billing-rates) for the current catalog, and retain `SECAPI-Meter-Class` and `SECAPI-Estimated-Cost` when a response supplies them. For a repeated path, use [a billing quote](/api-reference/platform/post-v1-billing-quote) before the loop; it estimates the current request but does not reserve credits.

Delivery work has its own meter families. Webhook and stream delivery use `delivery_events`; customer-configured monitor email recipients use `email_notifications`. If the account is budget-paused or lacks an active card or prepaid balance, paid delivery work is blocked rather than silently retried. Operational account emails do not use the monitor-email meter.

## Know the boundary

PAYG is for evaluation and internal use. It does not authorize redistribution, embedding, white-labeling, resale, or Bulk Factor Export. Read [plans and pricing](/plans-and-pricing) before shipping customer-facing output.
